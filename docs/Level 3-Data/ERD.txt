# AdotKazi Entity Relationship Diagram (ERD)

## Purpose

This document describes the logical entity relationships of the AdotKazi platform.

Rather than presenting one extremely large database diagram, the system is divided into bounded contexts.

Each bounded context owns its own entities while exposing only necessary relationships to other contexts.

This approach improves maintainability, scalability, and developer understanding.

---

# System Architecture

```text
                                    AdotKazi
                                        │
 ┌──────────────────────────────────────┼──────────────────────────────────────┐
 │                                      │                                      │
 │                                      │                                      │
Platform                         Recruitment                               IPT
 │                                      │                                      │
 │                                      │                                      │
Communication                     AI Platform                           Analytics
 │                                      │                                      │
 └─────────────────────────────── Administration ───────────────────────────────┘
```

Every module depends on the Platform bounded context.

Platform owns:

* Organizations
* Users
* Memberships
* Authentication
* Authorization
* Tenant isolation

# Cross-Bounded Context Relationships

```text
Platform
     │
     ├────────────► Recruitment
     │
     ├────────────► IPT
     │
     ├────────────► Communication
     │
     ├────────────► AI
     │
     ├────────────► Analytics
     │
     └────────────► Administration
```

Platform entities are referenced by every bounded context.

No bounded context may directly modify another bounded context's internal aggregates.

Interactions occur through:

* Domain Events
* Service APIs
* Read Models
* Shared Identifiers

# Tenant Isolation

Every tenant-owned entity contains:

* organization_id

Tenant isolation is enforced in:

* Database queries
* Application services
* API authorization
* Search indexes
* Analytics

No tenant may access another tenant's data.

---

# Database Standards

All entities follow the standards defined in:

* DATABASE_STANDARDS.md

Including:

* UUIDv7 primary keys
* Soft deletes where applicable
* UTC timestamps
* Audit fields
* Optimistic locking
* Foreign key constraints
* Indexing strategy

# Physical ERD

This document defines the logical architecture.

The physical database ERD should be generated automatically from the Prisma schema after implementation.

The generated ERD becomes the authoritative representation of database tables, columns, indexes, constraints, and relationships.

Manual maintenance of the physical ERD is discouraged to avoid documentation drift.
