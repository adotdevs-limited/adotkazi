# OBSERVABILITY.md

# AdotKazi Observability Architecture

**Version:** 1.0
**Status:** Platform Standard

---

# Purpose

This document defines the observability strategy for the AdotKazi platform.

Observability enables engineers to understand the internal state of the platform by collecting and correlating logs, metrics, traces, events, and health information.

The goal is to rapidly detect, investigate, diagnose, and resolve issues before they impact customers.

Observability is a core platform capability—not an optional operational feature.

---

# Vision

Every request, job, workflow, AI operation, and business event should be traceable from start to finish.

Engineers should be able to answer questions such as:

* What happened?
* When did it happen?
* Why did it happen?
* Who was affected?
* Which organization was affected?
* Which service failed?
* How can it be prevented?

---

# Goals

The Observability Platform must:

* Centralize logs
* Collect metrics
* Provide distributed tracing
* Monitor system health
* Detect anomalies
* Generate alerts
* Track business events
* Monitor infrastructure
* Support incident investigations
* Scale with the platform

---

# Core Principles

The platform follows these principles:

* Observe everything
* Correlate all telemetry
* Structure all logs
* Monitor business outcomes
* Automate alerting
* Minimize operational blind spots
* Avoid vendor lock-in

# The Five Pillars

AdotKazi collects five primary telemetry types:

1. Logs
2. Metrics
3. Distributed Traces
4. Business Events
5. Health Signals

Together they provide complete operational visibility.

---

# Structured Logging

Every service must produce structured logs.

Every log should contain:

* Timestamp
* Severity
* Service
* Module
* Environment
* Request ID
* Correlation ID
* Organization ID
* User ID (when applicable)
* Event Name
* Message

Logs should be machine-readable.

---

# Log Levels

Supported levels:

* TRACE
* DEBUG
* INFO
* WARN
* ERROR
* FATAL

Production defaults:

* INFO
* WARN
* ERROR

DEBUG logging should be disabled in production unless explicitly enabled.

---

# Logging Rules

Never log:

* Passwords
* Authentication tokens
* API secrets
* Encryption keys
* Personal identifiers beyond operational necessity
* Sensitive AI prompts unless explicitly permitted

Sensitive fields should be masked or redacted.

# Alerting

Alerts should be actionable.

Examples:

Critical:

* Database unavailable
* Authentication failure
* AI provider unavailable
* Queue backlog
* High error rate

Warning:

* Slow responses
* High memory usage
* Increased retries
* Elevated AI costs

Avoid alert fatigue by tuning thresholds.

# Service Level Objectives (SLOs)

Example targets:

* API availability ≥ 99.9%
* Authentication success ≥ 99.9%
* Opportunity search < 500ms (p95)
* Application submission < 2 seconds (p95)
* Email delivery queue < 1 minute
* AI request completion < 10 seconds (excluding provider delays)

SLOs should evolve as the platform grows.

---

# Error Tracking

Every exception should capture:

* Stack trace
* Environment
* Request ID
* Correlation ID
* Organization ID
* User ID
* Application version

Duplicate errors should be grouped automatically.

---

# Audit Correlation

Operational telemetry should correlate with audit logs where appropriate.

This enables complete reconstruction of sensitive administrative actions.

---

# Retention

Recommended retention:

| Data Type       |    Suggested Retention |
| --------------- | ---------------------: |
| Logs            |             30–90 Days |
| Metrics         |           12–24 Months |
| Traces          |              7–30 Days |
| Audit Logs      |  Per compliance policy |
| Business Events | Long-term (aggregated) |

Retention policies should be configurable.

---

# Recommended Technology

The architecture is vendor-independent.

Recommended stack:

* OpenTelemetry (telemetry collection)
* Prometheus (metrics)
* Grafana (dashboards)
* Loki (logs)
* Tempo or Jaeger (distributed tracing)
* Sentry (error tracking)

Equivalent alternatives may be substituted without changing application code.

---

# Security

Observability systems must:

* Respect tenant isolation
* Restrict dashboard access
* Mask sensitive data
* Encrypt telemetry in transit
* Authenticate dashboard users

Operational data should not expose confidential business information.

---

# Performance

Observability must:

* Minimize application overhead
* Use asynchronous telemetry export
* Batch log transmission
* Sample traces where appropriate
* Compress telemetry payloads

Instrumentation should not significantly impact user experience.

---

# AI Coding Agent Rules

When generating code, AI assistants must:

* Add structured logging for significant operations.
* Include correlation IDs in request flows.
* Instrument new APIs with metrics and traces.
* Avoid logging secrets or sensitive data.
* Expose health endpoints for new services.
* Emit domain events for business operations where applicable.

Instrumentation should be built into new features from the beginning.

# Definition of Done

A service is considered observable when:

* Structured logging is implemented.
* Metrics are collected.
* Distributed tracing is enabled.
* Health endpoints are exposed.
* Business events are emitted.
* Dashboards display meaningful telemetry.
* Alerts are configured for critical failures.
* Sensitive data is protected.
* Performance impact is acceptable.
* Operational teams can diagnose production issues using telemetry without requiring code changes.
