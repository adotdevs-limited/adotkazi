# AdotKazi Search Architecture

## Purpose

This document defines the search architecture for the AdotKazi platform.

Search is implemented as a dedicated platform service that provides fast, relevant, secure, and tenant-aware search capabilities across all modules.

The transactional database remains the source of truth.

Search indexes are optimized read models.

---

# Goals

The Search Platform must be:

* Fast
* Accurate
* Tenant-aware
* AI-ready
* Scalable
* Fault tolerant
* Cost-efficient
* Replaceable

---

# Search Architecture

```text
                      User

                        │

                 Search Request

                        │

                Search Gateway

                        │

     ┌──────────────────┼──────────────────┐

     │                  │                  │

 Meilisearch      PostgreSQL        Vector Search

     │                  │                  │

     └──────────────────┼──────────────────┘

                        │

                Search Response
```

Each search engine serves a different purpose.

---

# Search Technologies

## PostgreSQL

Used for:

* Primary keys
* UUID lookups
* Exact filtering
* Authorization checks
* Transactions

Examples

* Find candidate by ID
* Load opportunity details
* Verify permissions

---

## Meilisearch

Primary full-text search engine.

Used for:

* Opportunities
* Candidates
* Organizations
* Departments
* Skills
* Reports
* Notifications

Capabilities

* Typo tolerance
* Autocomplete
* Ranking
* Faceted filtering
* Synonyms
* Highlighting

---

## Vector Search

Supports semantic retrieval.

Examples

* Similar candidates
* Similar opportunities
* AI knowledge retrieval
* Resume similarity
* Report similarity
* Recommendation engine

Vector search is optional for MVP but fully supported by the architecture.

# Search Documents

Search indexes contain optimized documents rather than raw database rows.

Example Opportunity Document

```json
{
  "id": "...",
  "organizationId": "...",
  "title": "Senior Backend Engineer",
  "department": "Engineering",
  "employmentType": "Full-time",
  "location": "Dar es Salaam",
  "skills": [
    "Node.js",
    "PostgreSQL"
  ],
  "status": "Published"
}
```

Search documents are denormalized for speed.


---

# Index Synchronization

Search indexes are synchronized asynchronously.

Flow

```text
Database Updated

↓

Domain Event

↓

Search Queue

↓

Indexer

↓

Meilisearch

↓

Ready
```

The application never writes directly to the search engine.

---

# Search Events

Examples

* OpportunityPublished
* OpportunityUpdated
* CandidateCreated
* CandidateUpdated
* PlacementCompleted
* ReportSubmitted

Each event updates relevant search indexes.

---

# Tenant Isolation

Every indexed document contains:

* organization_id

Every query automatically filters by:

```text
organization_id
```

Cross-tenant search results are impossible.

---

# Permission Filtering

Search results must also respect authorization.

Example

A recruiter searches for:

```text
Frontend
```

Only opportunities and candidates the recruiter is authorized to access are returned.

# Performance

Targets

* Autocomplete < 100 ms
* Full-text search < 200 ms
* Semantic search < 500 ms
* Index update latency < 5 seconds

Large indexing operations execute in background workers.

---

# Fault Tolerance

If Meilisearch is unavailable:

* Exact lookups continue through PostgreSQL.
* Critical workflows remain operational.
* Search requests degrade gracefully.
* Index synchronization resumes automatically after recovery.

---

# Security

Search must enforce:

* Authentication
* Authorization
* Tenant isolation
* Input validation
* Rate limiting
* Audit logging

Search indexes never expose hidden or sensitive fields.

---

# Monitoring

Track:

* Index size
* Indexing latency
* Failed indexing jobs
* Search latency
* Query volume
* Cache hit rate
* Engine availability

Alerts should be generated for degraded performance.

# Definition of Done

The Search Platform is considered production-ready when:

* Search is isolated as a platform service.
* PostgreSQL remains the source of truth.
* Meilisearch indexes are asynchronously synchronized.
* Vector search supports semantic retrieval.
* Every search is tenant-aware.
* Authorization is enforced before results are returned.
* Search analytics are collected.
* Search degrades gracefully during outages.
* Monitoring and alerting are in place.
* The architecture remains provider-independent.
